# ATC — the engine under the game

C++23. A living economy: 1000 households and 100 firms trading, hiring and
setting prices with no central market-clearing. Nobody optimises; the macro
behaviour falls out of local decisions.

**This is the substrate, not the product.** `DESIGN.md` is the product — an
open-ended wizard-capitalism tycoon game. The engine exists so that a player
can eventually take a seat inside a world that was already running without
them. Read `DESIGN.md` first.

The model started as Lengnick's baseline ABM (JEBO 2013) and the rules still
follow it, because it is a good small economy. **We are not replicating the
paper.** Its success criteria, ensembles and replication findings are gone from
this file on purpose — if you want them, they are in git history before
2026-09-13.

## Commands

```bash
cmake -S . -B build && cmake --build build -j     # Release by default; builds atc_viewer if SDL3 is present
./build/atc_tests
./build/atc --seed 1 --burn-in 1000 --months 6000 --out output/run.csv
./build/atc --scenario scenarios/stimulus.scenario --out output/s.csv
./build/atc_viewer

./build/atc --identity-sheet output/marks.svg --identity-count 256 \
            --identity-locale turkish        # writes and exits; runs no months
```

Analysis in `scripts/` — `validate.py`, `ensemble.py`, `journal_stats.py` are
stdlib-only. `plot.py` needs matplotlib:

```bash
python3 -m venv .venv && .venv/bin/python -m pip install matplotlib pandas
.venv/bin/python scripts/plot.py output/run.csv
```

(There is no system `pip` module, but `venv`+`ensurepip` work fine. Verify
environment claims before repeating them.)

## Architecture

| File | Responsibility |
|---|---|
| `params.hpp` | Structural `constexpr` (layout, initial conditions) vs. the behavioural `Params` struct on `World`. Respect that boundary — see below. |
| `agents.hpp` | `Firm` and `Household` plain structs, `NO_FIRM`/`NO_HOUSEHOLD` sentinels |
| `world.{hpp,cpp}` | The agent arrays and the issuer accounts; `money_in_circulation()` (a measurement) and `books_balance()` (an assertion) |
| `ledger.{hpp,cpp}` | `transfer` — the only code allowed to write a balance; `Journal`, `Entry`, `Reason`; `MonthFlows` + `SummaryJournal` |
| `rng.{hpp,cpp}` | Deterministic seeded RNG, hand-rolled conversions |
| `network.{hpp,cpp}` | Household↔firm links (employment, shop connections) |
| `firm_decisions.{hpp,cpp}` | Monthly: wage, hire/fire, price |
| `household_decisions.{hpp,cpp}` | Monthly: shop search, job search, consumption budget |
| `daily.{hpp,cpp}` | Daily: shopping, then production |
| `month_close.{hpp,cpp}` | Wages, profits, reservation wages, deferred fires, demand rollover |
| `intervention.{hpp,cpp}` | The intervention log — how anything outside the model changes it |
| `scenario.{hpp,cpp}` | `Scenario` = seed + log; stream read/write, never paths |
| `scheduler.{hpp,cpp}` | The day/month tick; applies due interventions at month open |
| `recorder.{hpp,cpp}` | `Metrics`, `Recorder`, `CsvRecorder`, `CsvJournal` |
| `identity*.{hpp,cpp}` | Procedural firm logos and company names. `identity_glyphs.hpp` is generated by `scripts/gen_glyphs.py` — do not hand-edit |
| `main.cpp` | CLI. The only file allowed console I/O. |

### The tick

```
firm_decisions::run_monthly       wage, hire/fire marks, price
household_decisions::run_monthly  shop search, job search, consumption budget
settle_vacancy_bookkeeping        a still-open vacancy went unfilled
21 x daily::run_day               shopping (random order), then production
month_close::run                  wages, profits, reservation wages, fires, rollover
```

Ordering is load-bearing:
- `settle_vacancy_bookkeeping` runs *after* job search — that is when a vacancy
  is either taken or left standing.
- `pending_fire` is marked at month open and applied at month close, so a
  worker produces for the whole month. That is the one-month firing lag.
- `adjust_wage` runs before `adjust_workforce`, so it reads last month's
  `vacancy_went_unfilled` before this month's reset.
- `unsatisfied` is consumed by shop rewiring, then cleared, then re-accumulated
  over the 21 days.

### Viewer

Live SDL3 + ImGui (ImGui vendored at `third_party/imgui/`). It owns the `World`
and ticks it in its own frame loop. Scrubbing backward is exact re-simulation
from the nearest snapshot (every 50 months), never interpolation.

What the viewer *shows* is decided in a view-model layer (`viewer/cell.hpp`,
`model_agents`, `model_dist`, `model_time`, `model_steering`, `model_identity`),
separate from how it is drawn. Panels render `Cell`s and never reach into
`Firm`/`Household`. A `Cell` carries a raw number — that number is the sort key
— never a pre-formatted string, so a second skin reuses the decisions and
reimplements only the drawing. `Missing` is a cell kind, not a sentinel.

Testable logic lives in `viewer_core` and is covered without a window
(`tests/test_viewer_*.cpp`). The ImGui panels are untested; they only draw.

**Steering:** sliders for the behavioural parameters, money issuance, an audit
trail, scenario save. The rule that makes it safe: a slider **schedules** rather
than applies — the edit is appended to `App::log` for the month about to open.
So the slider keeps reading the old value until the month turns. That looks like
a bug and is not; the panel says so on screen.

Loading a scenario is CLI-only — `Sim` takes its log at construction.

## Invariants — do not break these

1. **Every movement of money balances.** `ledger::transfer` is the only code
   that writes `liquidity`, and it does one subtraction and one addition of the
   same `double`. A new module that moves money calls `transfer` or it is wrong.
   Money is created only by issuance, which is itself a balanced movement out of
   an issuer account. If a feature seems to need an exception, it is missing an
   issuer, not entitled to one.

   `transfer` rejects a movement that would push a **non-issuer** below zero
   (`ledger::Overdraft`), so a completed run is *proof* no account went negative.
   Issuer accounts may go negative freely — that negative number is what they
   have issued.

   If the books ever fail to balance, that is the highest-priority bug. Do not
   loosen a tolerance to hide it.

2. **Determinism.** Same seed → byte-identical run, including randomised agent
   order. All randomness flows through an explicitly passed `Rng&`. No `rand()`,
   no globals. `Rng::uniform`/`index`/`shuffle` are hand-rolled *on purpose* —
   the standard distributions are not portable across stdlib versions. Do not
   "simplify" them back to `std::uniform_int_distribution`/`std::shuffle`.

3. **Indices, never pointers,** between agents. Sentinel `0xFFFFFFFFu`.

4. **No virtuals on agent types.** `Recorder` is the sole exception. Variation
   arrives as fields and enums, never subclasses.

   3 and 4 are correctness properties, not optimisations. They keep agents
   trivially copyable, which is what makes `SimSnapshot` a plain assignment and
   therefore what makes the backward scrub byte-exact. A pointer or a virtual on
   `Firm` costs replay, scrubbing and save-games, not milliseconds.

5. **Core does I/O only through `Recorder`.** No `std::cout` in `src/` outside
   `main.cpp`.

6. Build warning-clean under `-Wall -Wextra -Wpedantic`.

### Two rules with teeth behind invariant 1

- **Structural vs behavioural parameters.** The test is: could a slider move it
  mid-run? `constexpr` in `params` if no (it defines memory layout or is
  consumed once at construction), `Params` on `World` if yes. `Params` is inside
  `SimSnapshot` for free, so restoring month 400 restores month 400's parameters.
  It must stay a plain aggregate.
- **A run is (seed + intervention log), not seed alone.** Interventions are
  applied at month open before any agent acts, ordered by `(month, seq)`.
  Parameters are addressed by *name* through one `constexpr` table
  (`intervention::param_specs()`), so there is no second list of ids to drift.
  This is what lets anything change a running world without breaking invariant 2
  — and it is the API a player seat will use (see `DESIGN.md`).

## Model rules that look like bugs but are not

- Firms **cut wages rather than go bankrupt** when payroll is unaffordable. The
  cut is bounded (`kMaxEmergencyWageCut`, `kMinWage`) — unbounded it reaches
  zero, and zero is absorbing, because every recovery channel is multiplicative.
- **Profits go out proportional to household liquidity** — the wealthy receive
  more. A deliberate stock-ownership proxy; it is the inequality engine.
- **Reservation wage never falls** when an employer cuts pay; the household
  searches harder. It falls 10% only while unemployed.
- **Price is gated, not clamped**: raised only while below the cap, lowered only
  while above the floor. Clamping turns a raise into a large cut.
- **Demand is recorded as *wanted*, not bought**, and telescopes across retry
  visits within a day. That is what makes a stocked-out firm expand. Do not read
  the `demand` series as consumer appetite — it counts one want at several firms.
- **The two shop-rewiring paths draw differently, on purpose.** Price comparison
  draws size-weighted (`random_unconnected_firm_by_size` — visibility) because an
  explicit price test then decides the switch. The rationed path draws unweighted
  (`random_unconnected_firm`) because it applies no price test, and a weighting
  there is unopposed. Unifying them once concentrated two thirds of the economy
  into dead firms. Do not unify them.
- Firms do not optimise, forecast, or maximise profit. That is the design.

## Things worth knowing before you measure anything

- **One seed is not a sample.** Bugs have hidden for 7000 months of seed 1 and
  died instantly on seed 5. Use `scripts/ensemble.py` before believing any claim
  about how the economy behaves.
- **Check per-firm distributions before trusting an average.** A "mean wage of
  16" was 67 dead firms at zero mixed with 33 healthy ones at 53.
- **A number that improves after a fix is not thereby validated.** Check what
  mechanism is producing it.
- **Discard the first timed run after a rebuild** — it reads ~30% slow cold.
  Interleave binaries when comparing.
- `transfer` runs ~855M times in a 6000-month run, ~82% of it profit
  distribution. Anything added to that path is a design decision, not a detail.
  But that 82% is a share of *movements*, not of runtime — profile before
  optimising on it.

## Known deferred items

Real, judged not worth fixing yet. Reconsider when touching that code.

- `network` has no bounds asserts on its index parameters.
- `daily.cpp`'s cost clamp does not reduce `bought`, so at machine-epsilon scale
  a firm can ship marginally more than paid for. Conservation unaffected.
- `household_decisions::run_monthly` has no direct test.
- Per-day `vector + iota + shuffle` allocates ~147k times per run. Irrelevant at
  1k agents.
- `month_close::run` takes no `Rng&`. Anything that moves money at month close
  will need one.
- `draw_cell`'s `col == 0` special case is a schema fact living in the panel —
  reordering columns would silently move row selection.
- `panel_agents.cpp` looks fields up by label string; a typo would print `0`
  rather than fail to compile.
- `identity_svg`'s shapes mirror the predicates in `identity.cpp` in two
  translation units; an edit to one can drift from the other.
- English, Japanese and German lexicons are unverified guesses. Only Turkish is
  speaker-reviewed; `Lexicon::verified` reports it and the CLI prints UNVERIFIED.
- `App::log` is appended from the panel while `Sim` holds a `const Log*`. Safe
  only because appends happen between steps on one thread.
